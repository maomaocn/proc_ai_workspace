# PRD：企业级 AI 智能采购与办公协同平台

版本：V1.1｜状态：待评审需求基线｜语言：简体中文

## 1. 项目目标

建设一个面向企业内部员工的 AI 采购助手：用户使用自然语言提出采购需求；系统检索采购制度、查询库存和供应商报价、生成建议，按确定性规则校验预算并提交人工审批；全过程可追溯、可恢复、可演示。

**教学目标**：在同一项目中真实使用 LLM、Embedding、RAG、Agent、Tool Calling、LangGraph、MCP、Agent Workflow、Agent Harness，而不是仅在 UI 中展示技术名词。

**双就业方向**：
- AI 应用开发：Python/FastAPI、数据模型、RAG、LangGraph、MCP、Harness、测试、部署。
- 企业 AI 工具/智能体搭建：Prompt、知识库配置、工作流设计、工具集成、业务验收；Dify/Coze 作为可选对照实验，不作为核心服务的硬依赖。

## 2. 角色与权限

| 角色 | 权限 |
|---|---|
| EMPLOYEE | 登录；查看知识库；创建/查看自己的采购申请；对自己的草稿编辑/提交；查看自己的任务记录 |
| APPROVER | EMPLOYEE 权限；查看分配给自己的待审批申请；批准/驳回并填写意见 |
| PROCUREMENT | 查看已批准采购单；更新采购执行状态；维护供应商及商品报价（演示场景） |
| ADMIN | 用户角色、知识库、采购规则、库存、供应商和审计日志管理 |
| TECH_ADMIN | 查看 Workflow/MCP/Harness 运行；受控测试白名单只读工具；不自动获得业务写权限 |

**安全要求**：后端逐请求鉴权、按角色与资源所有权授权；不能仅靠前端隐藏按钮。审批人不能审批自己提交的采购单。ADMIN 不能绕过审批规则直接执行采购。

## 3. 核心业务场景

### US-01 自然语言创建采购需求
- 输入：“采购 10 台笔记本，每台预算不超过 6000 元，优先符合公司标准的型号”。
- LLM 返回结构化草稿：品类、数量、单价上限、总预算上限、用途、备注、缺失字段。
- 必须使用 Pydantic Schema 校验；数量 > 0、单价 > 0；不完整信息需要追问，不能自行编造供应商或库存。
- 用户必须确认草稿，系统才持久化采购申请。
- 验收：输入标准示例生成正确字段；缺少数量时追问；模型返回不合法 JSON 时有可理解的错误提示或有限重试。

### US-02 企业采购制度问答
- ADMIN 上传 PDF/TXT/MD 格式采购制度，系统提取文本、切块、Embedding、入库。
- 用户可提问“6000 元以内笔记本需要几级审批？”；回答附来源文档名称、片段和页码（若可获取）。
- 未找到依据时明确表示“当前知识库未检索到足够依据”，不得虚构条款。
- 验收：上传示例制度后能检索对应片段；替换制度后新查询反映最新内容；用户无法看到无权限文档。

### US-03 查询库存与供应商
- Agent 调用 `inventory.search` 查询库存、`supplier.quote` 查询模拟报价。
- 结果包含商品 ID、型号、可用数量、价格、报价时间；禁止伪造实时外部报价。
- 库存、报价从本地数据库读取，初期不依赖真实 ERP。
- 验收：查询返回可验证的种子数据；参数不合法时工具拒绝；工具失败时有明确错误和降级响应。

### US-04 采购方案生成
- 综合用户需求、制度检索、库存和报价，形成方案（候选型号、数量、单价、总价、制度依据、风险说明）。
- 价格、合计金额由 Python Decimal 计算，不由 LLM 自行算账。
- LLM 的建议与实际业务规则校验结果必须分开呈现。
- 验收：金额与明细一致；缺少供应商报价时不能提交最终报价结论。

### US-05 采购审批
- 用户确认后提交采购申请；系统按数据库配置的确定性规则选择审批人/审批级别。
- LangGraph 工作流暂停等待审批；APPROVER 在 UI 中批准/驳回；审批操作具备幂等性。
- **示例规则（仅用于演示，可后台配置）**：总额 <= 10,000 元走部门负责人；> 10,000 元需部门负责人和财务顺序审批；如规则缺失则拒绝自动流转并提示管理员配置。
- 驳回必须填写理由；批准/驳回记录操作人、时间、原状态、新状态。
- 验收：审批前不会出现“已批准”；申请人不能自审；重复点击不会重复流转；审批恢复后可继续工作流。

### US-06 采购执行状态跟踪
- PROCUREMENT 仅能处理已批准采购单，更新为 ORDERED / RECEIVED / CLOSED；不可跳跃非法状态。
- 不接入真实支付、下单或真实供应商系统；所有外部采购行为为模拟操作。
- 验收：未批准申请无法进入 ORDERED；状态流转写入审计日志。

### US-07 Agent 执行追踪
- 每次 AI 请求生成 `run_id`，记录步骤、工具名、参数摘要、耗时、结果状态、错误码、token 用量（若可获取）。
- 对工具输入输出做敏感信息脱敏；不记录 API Key、明文密码或完整私人文档。
- 验收：可通过 run_id 查看调用链；超时、异常和重试能被定位。

### US-08 知识库管理
- ADMIN 上传/删除文档、查看索引状态（PENDING/INDEXING/READY/FAILED）、触发重建。
- 删除文档必须同时移除对应向量；失败可重试；按 `document_id` 过滤检索。
- 验收：重复上传同一文件不会产生重复活跃索引；删除后不可被检索。

## 4. 页面与交互

1. 登录页：账号密码，演示环境预置角色账号（首次登录必须修改密码可列为扩展）。
2. 工作台：对话框、最近任务、采购申请入口。
3. AI 采购助手：对话、结构化草稿确认、知识引用、工具调用状态、方案预览。
4. 采购申请列表与详情：筛选状态、查看审批链、审计事件。
5. 我的审批：待办、审批意见、批准/驳回。
6. 知识库管理：上传、状态、文档列表、删除、检索测试。
7. 管理后台：库存、供应商报价、审批规则、用户与角色。
8. Agent 运行记录：按 run_id 查看执行步骤、耗时和错误。

## 5. 采购申请状态机

`DRAFT -> SUBMITTED -> PENDING_APPROVAL -> APPROVED -> ORDERED -> RECEIVED -> CLOSED`

拒绝分支：`PENDING_APPROVAL -> REJECTED`；草稿可 `DRAFT -> CANCELLED`，提交后取消需另行定义审批规则，MVP 不支持。

- 状态更新在数据库事务中执行；使用版本号或行锁防并发冲突。
- 不允许由 LLM 直接写入审批状态或调用无授权的状态变更工具。
- 所有变更必须保存 `audit_event`。

## 6. MVP 边界与非目标

**必须实现**：本地模拟 LLM 与 Embedding；真实可替换的模型适配器；文档检索；采购意图解析；库存/报价工具；LangGraph 审批流程；一个 MCP Server 与 Client；Mini Harness；基本 Web UI；API；测试；Docker Compose；种子数据。

**暂不实现**：真实 ERP/SAP/钉钉/飞书集成、真实采购付款、供应商网站爬取、自动执行外部下单、微服务拆分、复杂多租户、生产级高可用和自动扩缩容、完整自主规划型通用 Agent。

## 7. 非功能要求

- 本地 `docker compose up --build` 可启动数据库、API、前端（如采用独立前端）及依赖服务。
- `.env.example` 完整列出环境变量；无 API Key 可启动 Mock 模式。
- API 统一响应错误码，业务错误不返回 500；配置 CORS 白名单；密码哈希；密钥只在环境变量中。
- 单次 Agent run 限制最多 8 次工具调用、最多 60 秒（默认可配置）；写操作不可自动重试。
- 读取工具超时默认 5 秒，最多重试 2 次；所有外部接口需设置超时。
- 对外部文本（用户输入、RAG 文档、MCP 响应）按不可信数据处理，不执行其中的“忽略规则”等指令。
- 关键流程单元测试 + API 集成测试；核心状态机、权限、金额计算必须有测试。
- 交付文档：README、架构说明、API 文档、测试说明、演示脚本、已知限制。

## 8. 验收场景（E2E）

1. 员工登录并输入 10 台笔记本需求，生成草稿并确认。
2. 系统检索公司采购制度，展示来源和制度要求。
3. 系统查询库存及报价，生成金额准确的候选采购方案。
4. 员工提交采购申请，进入人工审批队列。
5. 申请人尝试自审被拒绝；指定审批人批准后 LangGraph 继续。
6. 采购人员更新订单状态；申请人看到最新状态。
7. 管理员通过 run_id 查看 RAG、Tool Calling、MCP 和审批节点的日志。
8. 关闭真实 LLM Key，Mock 模式仍可完整跑通同样业务演示。

## 9. 教学分层

- **必做**：按指导完成 API、RAG、两个工具、单级审批、Mock 演示。
- **提高**：多级审批、MCP 接入、文档权限、日志查询、Docker。
- **挑战**：人工恢复后的幂等保障、RAG 评测、故障注入、复杂策略与性能分析。

## 10. 成功判定

优先以**可运行、可解释、可测试、可演示**衡量，不以框架数量、代码行数或界面华丽程度衡量。每个阶段都必须具备可运行的验收脚本。
